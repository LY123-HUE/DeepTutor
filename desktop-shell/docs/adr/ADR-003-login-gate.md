# ADR-003: 恢复登录门控 —— 未登录停在登录页，退出登录即回到登录页

## Status

Accepted（2026-09-18）

## Context

桌面端的登录交互经历了两代：

* **初代（门控）**：未登录停在启动页，无法进入应用。问题：登录失败的全部注意力
  压在一个入口上，且把所有本地功能挡在门外。
* **二代（不拦启动，ADR-002 时期）**：服务就绪即进应用，登录做成应用左下角的
  常驻按钮。问题在分发场景暴露：大量用户**未登录就进入应用**，看到的是空模型
  列表、对话直接报错——「软件不可用」的表现和「没登录」的原因之间没有可见联系，
  反而制造了支持成本。

同时产品对齐了 WorkBuddy 桌面端的登录交互基准：启动时未登录显示品牌登录页
（居中吉祥物 + 一句话 + 黑色登录按钮），点击唤起浏览器到平台注册/登录；退出登录
回到该页，软件功能不可用。EduBuddy 作为 Tokengine 的分发客户端，账号体系本就
绑定平台（模型、额度均来自平台），「未登录可用」没有真实场景。

## Decision

1. **启动门控回归**：本地服务就绪后检查登录态（`AuthManager.has_usable_token()`，
   含用户手配令牌的兜底），未登录则窗口停留在重做的登录门控页——浅色、居中
   吉祥物 + 「EduBuddy，我帮你」+ 黑色胶囊登录按钮（`desktop/splash.py` 重写）。
2. **登录成功 → 自动进入应用**：会话主循环（`desktop/main.py::run_session`）
   在门控页等待 OAuth 完成（PKCE + 本机回环，链路与二代完全一致），成功后
   令牌与按 `model_type` 分流的可用模型写入 `model_catalog.json`，然后
   `load_url` 进入应用。
3. **退出登录 → 回到登录页**：应用内账号菜单「退出登录」吊销令牌、摘除
   Tokengine catalog 配置后，向会话主循环发信号，主循环 `load_html` 重载登录
   门控页——应用界面随页面卸载而不可用。再次登录成功后重新进入应用。
4. **保留开发旁路**：`DEEPTUTOR_DESKTOP_SKIP_LOGIN=1` 跳过门控（离线/开发）。
5. **移除「稍后再说」**：登录从「可推迟的增量动作」变回「使用前置条件」，
   门控页不再提供跳过入口。

## Consequences

**变简单的：**

* 「软件不可用」与「没登录」的因果可见——登录页就是应用的唯一入口，模型为空、
  对话报错这类支持问题从入口处消失；
* 分发链路职责清晰：装机 → 登录 → 可用，无需解释「为什么模型列表是空的」；
* 登录页与启动页合并为同一页面，启动状态反馈不丢。

**变难的 / 需要接受的：**

* 未登录时本地功能（知识库管理、笔记等纯本地能力）不再可用——这是刻意取舍：
  目标用户是平台账号用户，本地优先不是产品主张；
* 登录链路故障（平台不可达、回调被防火墙拦截）会直接挡住所有用户，门控页必须
  如实显示失败原因（「登录未完成：<平台错误>」红字）并支持无限次重试；
* 会话主循环引入了 门控 ↔ 应用 的状态往返，退出登录的页面导航依赖
  `load_html` + js_api 桥的可用性（pywebview 对同窗口 load_html 注入桥是
  文档化行为，初代启动页已验证）；
* 手配令牌的用户（`configured`）仍可跳过门控——保留「绝不误伤用户手动配置」
  的既有原则（见 `auth/catalog.py`），代价是这类用户不会被动推向平台登录。

**中立变化：**

* 应用内左下角按钮与菜单保持不变（二代成果），它现在承担「登录后的账号管理」
  与「门控页之外的第二个登录入口」两个角色。

## Addendum: 「退出登录闪回应用」事故（2026-09-18）

**现象**：应用内退出登录后，日志显示信号链完整（`logged out` → `logout
detected; returning to login gate`），但 7ms 后会话主循环 `navigating` 回应用，
登录页被 `load_url` 覆盖，用户带着已吊销令牌停留在应用里（401 僵尸会话）。

**根因（两层叠加）**：

1. **陈旧的登录等待结果**。`AuthManager._done` 是一次性完成事件：应用内
   「切换账号」再次登录成功时 `_finalize` 置位 `_done`，但此刻会话主循环在等
   退出信号、无人消费它。退出登录后门控等待 `wait_done()` 立刻拿到这份陈旧的
   `{"ok": True}` 直接放行——这是 7ms 内闪回的直接原因。
2. **注销后的门控判定是可跳过的**。`run_session` 每轮复评 `_gate_needed()`
   （依赖 `has_usable_token()`），catalog 里残留的手配 api_key 会让它返回
   False，即使走到 `load_html(登录页)` 也会被紧随的 `load_url` 覆盖。

**决策**（两层防御，缺一不可）：

* `AuthManager.logout()` 在清凭据的同时清掉 `_done`/`_result`/`_pending_*`——
  在途登录的回调会因缺 verifier 得到 `session_lost` 失败结果，无法再伪造陈旧
  成功（治本）；
* `run_session` 引入 `force_gate`：注销后下一轮**无条件**停在门控页等一次全新
  登录，不复评 `has_usable_token()`——注销后回门控是确定性动作，不被任何残留
  状态跳过（防御）。`SKIP_LOGIN=1` 仅旁路启动门控，注销后仍回门控页。

**教训**：注销语义必须是「状态机的确定性迁移」，不能委托给「重新计算登录态」
这类可被残留数据影响的判定；一次性完成事件（`Event`）跨消费方传递时，必须
明确「谁在什么时机消费」，否则陈旧结果会在下一个等待者身上引爆。
